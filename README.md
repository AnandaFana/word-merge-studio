# Word Merge Studio

一个在本机浏览器中运行的 Word 双栏对比与合并工具。打开左右两份 `.docx`，逐项选择需要的内容，指定左侧或右侧作为格式基准，再导出合并后的 Word。

这是可运行的第一版，适合以普通段落、同结构表格为主的文档修订。复杂 Word 结构采用保留或拒绝策略，具体边界见下表。不会把文档转成 HTML 再重建 Word。

## 启动

需要 Node.js **22.12+**，建议使用 Node.js 22 LTS 或更新的 LTS。首次安装依赖需要联网；安装完成后，使用工具处理文档不需要联网，也不需要 Microsoft Word、Python 或后端服务。

Windows 双击 **`start.cmd`** 即可。启动窗口需要保持打开，关闭工具时按 `Ctrl+C`。优先使用 5173；端口占用时自动尝试 5174、5175 等，直到找到空闲端口，并自动打开实际地址。不会终止已经运行的服务。终端打印的 `Local` 地址为准。

也可以手动启动：

```powershell
cd word-merge-studio
npm.cmd ci --cache .npm-cache
npm.cmd run dev
```

打开 [本地工作台](http://127.0.0.1:5173)。首次进入可以点击“体验示例”，无需准备测试文档。macOS / Linux 使用 `npm ci` 和 `npm run dev`。

## 分享给同事

从 GitHub 仓库页面选择 **Code → Download ZIP** 并解压，或使用 Git 克隆仓库。在项目文件夹中双击 `start.cmd` 即可启动；首次运行需先安装 Node.js 22.12+，并联网下载依赖。源码中自带合成演示，同事不需要你的 Word 原文件。

每个人在自己的电脑上打开自己的文档，文档内容不会上传到 GitHub。私有仓库需要先给同事仓库访问权限，公开仓库则可直接分享仓库链接。不要把工作目录中的 Word、`.qa/`、缓存或账号凭据加入 Git。

## 使用流程

1. 在左右两侧分别打开或拖入 `.docx`。旧版 `.doc` 请先用 Word 另存为 `.docx`。
2. 选择“文档底稿：左侧文档 / 右侧文档”。这份文档控制页面设置、页眉页脚与全局样式。
3. 在“差异审阅”中查看段落级对齐与逐字差异；选左、选右、都保留（左后右）或都不要。
4. 可搜索正文、只看差异、跳转上一处/下一处，也可全部选左/全部选右。撤销最多保留 100 次操作。
5. “原版预览”并排展示两份原文件；“合并预览”查看当前选择的输出。
6. “导出 Word”生成新文件并请求下载；如果浏览器拦截自动下载，点击生成后的“保存”链接。未确认项默认沿用底稿；不会写回或覆盖源文件。建议通过 `start.cmd` 在系统浏览器使用；内置浏览器的下载落盘尚未确认，详见验证记录。
7. 可下载不含正文的 JSON 选择记录，用于检查操作。当前不支持导入记录恢复会话，刷新页面会清空选择。

更换任意源文件会清空选择。切换格式基准也会清空选择，但可通过撤销恢复原基准和选择。

## 文字和格式分别选择（v0.2）

例如要把右侧文字合入左侧，同时用左侧正文格式：

1. 文档底稿选“左侧文档”。
2. 在目标块点击“选右”，选择右侧文字。
3. 将这一块的“段落格式”设为“左侧段落格式（整段统一）”。
4. 确认显示“内容：右侧 / 格式：左侧统一”，然后预览、导出。

也可以采用左侧文字、右侧段落格式。格式选项独立于内容选项，即使文字相同也能单独调整，撤销会同时恢复当次格式操作。选择记录现为 v2，包含全局模式及逐块格式选择。

| 格式选项 | 行为 |
| --- | --- |
| 跟随全局 + 精确保留底稿 | 保留底稿各片段的原格式，包括局部粗体、不同字号；兼容旧版默认行为 |
| 左侧 / 右侧段落格式 | 使用指定侧对应段落的段落属性，并按字符数最多的主体字符格式统一整段，避免短片段的异常格式混入 |
| 智能匹配底稿 | 本地规则识别标题、正文、列表，优先对应同类段落；新增或类型不符时从底稿同类段落里选择常用格式；无同类模板时回退到基准默认样式，不将附近标题格式套给正文 |

全局“智能匹配底稿”作用于可处理的全部正文块，包括未改字和文字相同的段落；单块明确选择左/右格式优先于全局模式。复杂块仍原样保留，跨段结构锁定时禁用智能模式。界面显示左右段落的角色、字体、字号供核对。

**整段统一会清除局部粗体、斜体、上下标等字符差异**，因此默认仍为精确保留；有需要保留的强调或上下标时请使用原模式。智能是可解释的本地启发式规则，不调用在线 AI，不保证所有标题或正文都识别正确。

跨侧格式先展开常见的 `docDefaults`、段落/字符样式和 `basedOn`，再解析常见主题字体及颜色，写成直接属性，避免左右相同样式 ID 指向不同字体。未指定的跨侧字体回退为西文 Calibri、中文宋体，未指定字号回退 11pt。跨侧自动编号、浮动框架、条件样式、段落主题边框/底纹以及无法解析的主题字体会拒绝迁移。复杂样式级联、样式 toggle 语义及目标默认段落样式中的特殊属性未承诺完整保真，请通过预览核对。表格选格式只影响单元格段落文字；几何、边框、底色仍来自文档底稿。

## “保留一种格式”具体是什么意思

在默认“精确保留底稿”模式且没有独立格式覆盖时，假设选择左侧作为基准，某段采用右侧文字：

- 输出从完整左侧 DOCX 文件包复制，只修改 `word/document.xml`。
- 左侧 `styles.xml`、主题、编号定义、图片文件、关系文件、页眉页脚等文件内容保持逐字节一致。
- 对应段落保留左侧段落属性；未变化文字保留左侧对应字符的字体、粗体等 run 属性；新增或替换文字继承左侧修改位置的字符格式。
- 新增段落没有对应底稿段落时，继承附近非空普通段落的段落属性和首个显式字符属性。不会自动继承该段落的自动编号；没有可用段落时使用底稿默认样式。
- 同结构表格只修改单元格里的文字，表格宽度、边框、底色、合并单元格等来自底稿。
- 没有选择任何改动，或全部明确选底稿时，输出与底稿整个文件逐字节一致。

这里的格式保留保证针对文件结构及基准属性。更换文字长度会影响换行、分页和行内位置，不能保证最终页数或每个像素不变。新增段落的格式继承是启发式选择，请检查标题与正文的对应关系。

## 支持范围

| 内容 | 当前行为 |
| --- | --- |
| 普通段落、中文/英文、空段落、制表符、普通换行 | 支持对比、替换、插入、删除、两侧都保留 |
| 同结构表格 | 支持逐单元格段落文字合入，保留基准表格格式 |
| 新增表格、改变行列、改变合并单元格、表格与段落互换 | 禁止跨侧合入；可将含所需表格的一侧设为底稿 |
| 底稿图片、公式、超链接、文本框、嵌入对象、分节段落、未知正文结构 | 原样保留该块；禁止对该块跨侧合入或删除 |
| 另一侧的图片、公式、超链接、嵌入对象等 | 尚未支持资源关系迁移；操作按钮禁用并解释原因 |
| 跨段域、修订、移动修订、书签、批注范围、权限范围 | 整组对比只允许原样导出基准，请先在源文件副本中处理 |
| 正文直接格式差异 | 标记供审阅；默认使用底稿，可独立选择左/右段落格式或智能统一 |
| 样式定义、主题、页眉页脚、脚注等非正文部分的差异 | 不纳入差异列表，始终采用底稿版本 |
| 宏、数字签名、加密、旧版 `.doc`、Strict OOXML | 不支持，给出错误提示 |

正文差异中的“格式差异”基于清理编辑标记后的 XML 比较，可能包含无视觉影响的 run 拆分变化；它不是完整的样式继承或视觉差异检测。复杂块一律要求审阅，即使文字相同，也不能据此断言图片资源相同。

段落对齐先找相同文本块作为锚点，连续替换区按顺序配对。大规模重写、段落拆分/合并、段落移动不提供语义匹配或三方冲突识别，应逐项确认。选择“都保留”会实际复制两侧内容；文字相同的格式差异也会重复该段。

规模限制：单文件 25 MB；解压总量 100 MB；最多 5000 个 ZIP 条目、2500 个正文块；单块 2 万字符、总计 50 万字符。大文档仍可能短暂占用浏览器主线程，超时会停止该操作并提示拆分。

## 技术栈与目录

- React + TypeScript + Vite：双栏交互与静态应用。
- JSZip：读取原文件包、复制基准文件包并输出 DOCX。
- 浏览器 DOMParser / XMLSerializer：定点处理 OOXML。
- `diff`：正文块对齐与字符差异。
- `docx-preview`：隔离 iframe 中的只读预览，不参与输出文件生成。
- Vitest + jsdom：合并契约与真实文档回归。

```text
src/engine.ts       DOCX 读取、结构限制、差异与格式保留合并
src/formatting.ts   段落角色识别、样式展开、独立格式选择与整段统一
src/App.tsx         双栏审阅、选择、撤销、导出与帮助
src/Preview.tsx     隔离预览
src/demo.ts         纯合成示例，不包含用户原文件
src/style.css      自适应界面
tests/engine.test.ts 结构、格式、内容与本地文件回归
docs/RESEARCH.md    开源方案调研与选型
docs/VALIDATION.md  已验证项目和剩余边界
start.cmd          Windows 启动入口
```

## 构建与验证

```powershell
npm.cmd test

npm.cmd run preview
npm.cmd audit --cache .npm-cache
```

构建产物在 `dist/`，可以使用静态 HTTP 服务运行；直接双击 `dist/index.html` 的 `file://` 方式不支持 ES 模块加载。不要把整个工作目录上传到网站，只部署 `dist/`。本任务未进行公网部署。

测试会在根目录恰好有两份 `.docx` 时自动运行本地双向合并回归，否则跳过该项；不会把真实文档复制到应用、提交或公共示例。默认测试不保存合并文件。设置 `WRITE_QA=1` 才将实际文档的测试输出保存到被忽略的 `.qa/` 中，仅用于本地检查。

## 隐私与预览

应用没有上传 API、账号、遥测、外部 CDN 或远程字体。文件内容在浏览器内存中处理。开发服务器只监听 `127.0.0.1`，并禁止直接通过 HTTP 读取目录中的 DOCX、QA 输出和 npm 缓存。DOCX 预览置于不允许脚本、外部请求和顶层导航的 iframe，禁用 HTML altChunk 渲染。

`docx-preview` 受浏览器排版能力限制，自动分页与 Word 不完全一致。最终文档请在 Word / WPS 中查看，尤其是新增长段落后的分页。当前工具适合本机可信文档处理，尚未按公开上传服务标准进行渗透和兼容性测试。

## 后续扩展

优先做基于相似度的段落移动/拆分匹配、合并会话保存恢复，以及图片/超链接资源关系迁移。随后考虑脚注、编号跨文档重映射和多节文档。若要 Office 引擎级比较、修订或打印排版，可以增加独立的 Windows Word / .NET Open XML 后端适配层，同时保留当前本地审阅界面。
